# پایش سالمند — نسخهٔ اصلاح‌شدهٔ مهندسی

**پایهٔ قابل آزمون برای پایلوت تحت نظارت؛ محصول پزشکی/ایمنی تأییدشده یا آمادهٔ فروش نیست.** این نسخه همچنان از YOLO Pose، ByteTrack و قواعد زمانی استفاده می‌کند؛ مدل جدیدی روی سالمندان آموزش داده نشده است.

ابتدا **`REVIEW_FA.md`** را بخوانید: بررسی تمام قابلیت‌ها، خطاهای منطقی، راه‌حل مثال دو ساعت بی‌حرکتی، محدودیت‌ها و مسیر تجاری‌شدن. تغییر قرارداد خروجی‌ها در **`MIGRATION.md`** و محدودهٔ آزمون در **`TESTING.md`** آمده است. اسناد `legacy_docs/` فقط برای مقایسه با نسخهٔ ورودی نگهداری شده‌اند.

## مهم‌ترین تغییرها

- استراحت ظاهری روی تخت/صندلی از بیهوشی و سقوط جدا شده است؛ سکون در تخت اثبات خواب یا سلامت نیست.
- سیاست اختیاریِ بی‌حرکتی با برنامهٔ مراقبتی، به‌جای تایمر عمومی برای همهٔ مکان‌ها.
- افت سریع روی تخت یا قطع دید هنگام افت، بی‌صدا ایمن فرض نمی‌شود.
- هندسه و اعتبارسنجی نواحی بهتر شده؛ کف خالی دیگر مجوز اعلام سقوط روی کل تصویر نیست.
- حادثه و صف ارسال در SQLite نگهداری می‌شوند و با restart یا گم‌شدن Track از بین نمی‌روند.
- تأیید دریافت، پایان وضعیت تصویری و بستن حادثه سه چیز جدا هستند.
- فرستندهٔ مستقل HTTPS با تلاش مجدد، جلوگیری از ارسال هم‌زمان یک پیام و بررسی heartbeat نوشته شده است.
- سلامت تصویر، تازگی محلی تصمیم و چرخش CSV کنترل می‌شوند.

## ۱. نصب

پایتون ۳٫۱۱ برای محیط هدف پیشنهاد می‌شود؛ بازهٔ اولیهٔ پروژه ۳٫۱۰ تا ۳٫۱۲ بوده است. محیط اجرای آزمون این تحویل متفاوت است و در TESTING.md ذکر شده است.

```bash
python -m venv .venv
```

لینوکس/مک:

```bash
source .venv/bin/activate
```

ویندوز PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

سپس:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

برای GPU، PyTorch/CUDA مناسب دستگاه را جداگانه از مرجع رسمی آماده کنید. فایل وزن مورد اعتماد COCO-17 مانند `yolo11s-pose.pt` لازم است. وزن در این ZIP وجود ندارد. اولین اجرای عادی YOLO ممکن است وزن را دانلود کند. برای منع دانلودِ خودکار وزن در مسیر برنامه از `--require-local-model` و مسیر موجود استفاده کنید؛ این پرچم جای فایروال، بررسی وابستگی‌ها یا سیاست آفلاین را نمی‌گیرد.

وابستگی‌ها بازهٔ نسخه دارند، نه lock تولیدِ تأییدشده. پس از آزمون روی سخت‌افزار هدف، محیط و hash وزن را تثبیت و از نظر امنیت/مجوز بررسی کنید. `NOTICE.md` را بخوانید.

تست هسته به NumPy نیاز دارد؛ تست مسیر ویدئو به OpenCV هم نیاز دارد. تست‌ها YOLO واقعی را اجرا نمی‌کنند:

```bash
python -m unittest discover -s tests -v
python -m compileall -q .
python demo_floor_lying.py
python monitor.py --config config.json --care-config care_config.json --print-config
```

سناریوی دو ساعت سکون در تخت و صندلی در `tests/test_care_policy.py` قرار دارد؛ زمان مصنوعی جلو برده می‌شود و اجرای آن دو ساعت طول نمی‌کشد. این آزمون سیاست هشدار است، نه اثبات عملکرد مدل روی فیلم دو ساعته.

## ۳. نواحی را برای همان دوربین کالیبره کنید

```bash
python select_zones.py --source 0 --config config.json
```

- `B`: سطح تخت؛ `F`: کف قابل‌دیدن؛ `R`: سطح صندلی/مبل استراحت.
- رأس‌ها را به ترتیب دور محیط کلیک کنید؛ رأس اول را در انتها تکرار نکنید.
- `U`: حذف آخرین رأس، `C`: پاک‌کردن ناحیه، `S`: ذخیره، `Q`: لغو.
- برای ویدئو: `--source room.mp4 --at 10`.
- روی سرور بدون نمایشگر، مختصات نرمال‌شدهٔ همان تصویر را دستی وارد کنید.

محدوده‌ها عمداً خالی تحویل داده شده‌اند: تصویر اتاق شما موجود نیست. بدون کف، ماندن روی کف غیرفعال است و افت سریع ممکن است فقط درخواست بررسی تأییدنشده ایجاد کند. بدون تخت/صندلی، استراحتِ آن ناحیه قابل تشخیص نیست.

کف را روی تخت/مبل نکشید. هر سه لنگر شانه، لگن و مرکز تنه برای عضویت بررسی می‌شوند؛ بدنی که مرز دو ناحیه را قطع کند ممکن است مبهم شود. هم‌پوشانی‌ها خودکار اصلاح نمی‌شوند. بعد از جابه‌جایی، زوم، تغییر crop یا نصب دوبارهٔ دوربین، دوباره کالیبره کنید. تغییر ابعاد تصویر توقف اعتماد به کالیبراسیون را ایجاد می‌کند؛ بعد از بازبینی نیاز به راه‌اندازی مجدد دارید. جابه‌جایی با رزولوشن ثابت لزوماً خودکار شناسایی نمی‌شود.

## ۴. تنظیم سیاست استراحت و بی‌حرکتی

در `care_config.json` پیش‌فرض:

```json
{
  "inactivity_enabled": false,
  "care_plan_id": "",
  "nonrest_checkin_s": 900.0,
  "rest_checkin_s": null,
  "expected_presence": false,
  "coverage_checkin_s": 15.0,
  "min_pose_quality": 0.6,
  "motion_threshold": 0.15,
  "movement_reset_s": 2.0,
  "max_gap_s": 0.65,
  "ack_timeout_s": 60.0,
  "resolution_reminder_s": 300.0
}
```

این اعداد پیش‌فرض مهندسی‌اند، نه استاندارد پزشکی یا زمان امن انتظار.

برای فعال‌سازی بی‌حرکتی:

1. با مسئول مراقبت مشخص کنید کدام ناحیه‌ها استراحت طبیعی‌اند و چه چیزی نیاز به بررسی دارد.
2. `care_plan_id` را یک برچسب غیرحساس و مستند قرار دهید؛ نه نام/اطلاعات پزشکی شخص.
3. `inactivity_enabled` را فعال کنید و زمان‌ها را با برنامهٔ تأییدشده تنظیم کنید. مقدار ۹۰۰ ثانیه صرفاً مثال است.
4. `rest_checkin_s=null` یعنی سکون طولانی در تخت/صندلی به‌تنهایی درخواست بررسی نمی‌سازد. اگر بازدید زمان‌بندی‌شده لازم است مقدار مشخص بدهید؛ این هنوز تشخیص بیهوشی نیست.
5. `expected_presence` را فقط وقتی فعال کنید که غیبت از دید واقعاً طبق برنامه نیازمند بررسی باشد. برای اتاقی که افراد آزادانه وارد و خارج می‌شوند فعال‌کردن آن می‌تواند اعلان اضافی بسازد.

برنامهٔ فعلی به همهٔ Trackهای یک دوربین اعمال می‌شود؛ هویت فردی را شناسایی نمی‌کند. فایل نمونه را بدون بازبینی به‌عنوان تنظیم تولید استفاده نکنید.

## ۵. اجرای پایش

وب‌کم، فقط لاگ و پروندهٔ محلی:

```bash
python monitor.py --source 0 --config config.json --care-config care_config.json --csv logs/monitor.csv --incident-db logs/incidents.sqlite3 --site-id room01 --show
```

بدون `--show` هیچ پنجره‌ای باز نمی‌شود. برای مدل محلی و GPU:

```bash
python monitor.py --source 0 --model models/yolo11s-pose.pt --require-local-model --device 0 --imgsz 960 --config config.json --care-config care_config.json --csv logs/monitor.csv --incident-db logs/incidents.sqlite3 --site-id room01
```

برای ویدئوی آزمایشی از مسیر لاگ و دیتابیس جدا استفاده کنید:

```bash
python monitor.py --source room.mp4 --config config.json --care-config care_config.json --csv logs/replay.csv --incident-db logs/replay.sqlite3
```

**ویدئوی تاریخی را به دیتابیس/گیرندهٔ زنده وصل نکنید.** زمان منبع ویدئو برای تشخیص است، اما deadline رسیدگی براساس زمان واقعی اجرا محاسبه می‌شود. worker با `--watch-site` برای فایل تاریخی راه‌اندازی نشود.

### دوربین شبکه و رازها

URL واقعی دوربین را با ابزار مدیریت راز/محیط سیستم‌عامل در متغیر `ELDERCARE_SOURCE` قرار دهید؛ مقدار واقعی را در README، git یا آرگومان خط فرمان ننویسید:

```bash
python monitor.py --source-env ELDERCARE_SOURCE --config config.json --care-config care_config.json --csv logs/monitor.csv --incident-db logs/incidents.sqlite3 --site-id room01
```

این برنامه URL را در متادیتای خودش ذخیره نمی‌کند، اما محیط پردازش و لاگ درایورها هم باید محافظت شوند. برای شبکه، حساب حداقلی و محدودسازی شبکه توصیه می‌شود.

گزینه‌های مهم:

- `--max-frame-age 1.0`: حداکثر سن محلی فریم/نتیجه برای ورودی زنده، شامل زمان استنتاج؛ اگر سخت‌افزار کند باشد نتیجه کنار گذاشته می‌شود و مشکل فنی ثبت می‌شود.
- `--stream-timeout 10`: قطع جریان موجب توقف با کد ۲ می‌شود؛ reconnect درون پردازش نداریم.
- `--check-frame-health`: بررسی سلامت تصویر برای فایل ویدئو هم فعال شود؛ برای زنده خودکار فعال است.
- `--max-csv-bytes 20971520 --csv-backups 5`: کنترل چرخش CSV.
- `--max-seconds 60`: توقف بعد از زمان منبع تعیین‌شده؛ `--video-fps` فقط برای fallback زمانی فایل.
- `Q` / `Esc` در پنجره یا `Ctrl+C`: خروج. توقف زنده یک موضوع نبود پایش ثبت می‌کند.

## ۶. ارسال واقعی به سامانهٔ مراقب

**پایش به‌تنهایی پیامک، تماس یا اعلان موبایل نمی‌فرستد.** SQLite و چاپ کنسول به معنی اطلاع مراقب نیست.

یک گیرندهٔ HTTPS مورد اعتماد لازم است که Bearer token را اعتبارسنجی کند، `Idempotency-Key` را حذف تکرار کند، رویدادها را با زمان/ترتیب پردازش کند و اعلان را به تیم واقعی برساند. URL و token را با مدیریت راز در این دو متغیر قرار دهید:

- `ELDERCARE_WEBHOOK_URL`
- `ELDERCARE_WEBHOOK_TOKEN`

سپس در **پردازش مستقل**:

```bash
python delivery.py --db logs/incidents.sqlite3 --watch-site room01 --stale-seconds 30
```

`room01` باید با `--site-id` پایش زنده یکسان باشد. اگر heartbeat از اول وجود نداشته باشد، نگهبان بعد از شروع خودش نبود پایش را اعلام می‌کند؛ ترتیب راه‌اندازی را در بهره‌برداری مدیریت کنید.

برای بررسی یک نوبت بدون سرویس دائمی:

```bash
python delivery.py --db logs/incidents.sqlite3 --once
```

اگر URL تنظیم نشده باشد، worker صریحاً هشدار می‌دهد و چیزی ارسال نمی‌کند. پیام‌ها در صف می‌مانند. اگر URL تنظیم باشد، همین دستور می‌تواند یک پیام واقعی ارسال کند. این بسته در زمان ساخت به گیرندهٔ واقعی متصل نشده است.

فرستنده فقط HTTPS معتبر می‌پذیرد و redirect را دنبال نمی‌کند. کد 2xx فقط رسید انتقال است و پرونده را ACK یا Resolve نمی‌کند. ارتباط با سازمان مراقب و تأیید انسان باید جداگانه آزمون شود. ارسال at-least-once است؛ در خرابی بین رسید شبکه و ثبت موفقیت در دیسک، پیام می‌تواند دوباره ارسال شود.

روی لینوکس/ویندوز، دو پردازش را با مدیر سرویس مناسب و restart کنترل‌شده اجرا کنید. خودِ worker، ظرفیت صف، دیسک، ساعت سیستم، تأخیر اعلان و کارکرد گیرنده نیازمند مانیتورینگ بیرونی‌اند. خرابی برق/میزبان با نگهبان روی همان میزبان حل نمی‌شود. هیچ سرویس مدیریتی در سیستم شما توسط این تحویل نصب نشده است.

## ۷. رسیدگی به حادثه

فهرست پرونده‌های باز و صف:

```bash
python incident_cli.py --db logs/incidents.sqlite3 list
python incident_cli.py --db logs/incidents.sqlite3 delivery-status
```

شناسهٔ واقعی پرونده را از فهرست بگیرید:

```bash
python incident_cli.py --db logs/incidents.sqlite3 ack INCIDENT_ID --operator caregiver01 --note "Review accepted"
python incident_cli.py --db logs/incidents.sqlite3 resolve INCIDENT_ID --operator caregiver01 --note "In-person review completed; outcome recorded in care system"
```

متن مثال را با نتیجهٔ واقعی و حداقل اطلاعات لازم جایگزین کنید. فقط چون تصویر دوباره طبیعی شده پرونده را نبندید. `ACK` به معنی رسیدن کمک یا بستن پرونده نیست؛ اگر در موعد مقرر رسیدگی/بستن انجام نشود یادآوری ارسال می‌شود. اولویت بالاتر ناشی از بی‌پاسخی، به معنی تشخیص وخامت پزشکی نیست.

این CLI محلی احراز هویت سازمانی ندارد؛ مجوز حساب/فایل سیستم‌عامل مرز دسترسی است. نام اپراتور یک ورودی حسابرسی است، نه اثبات هویت. برای محصول چندکاربره، RBAC و احراز هویت مستقل لازم است.

## ۸. قرارداد خروجی‌ها

- `standing`, `sitting`, `walking`, `lying`: تخمین ظاهر/فعالیت؛ نه وضعیت بالینی.
- `resting_in_bed`, `resting_in_chair`: زمینهٔ استراحت؛ نه تأیید خواب.
- `possible_postural_sway`: نوسان ظاهری؛ نه پیش‌بینی معتبر سقوط.
- `rapid_descent`, `rapid_descent_high_speed`: شواهد نزول؛ به‌تنهایی تشخیص غش نیستند.
- `possible_fall`, `prolonged_floor_lying`: درخواست رسیدگی فوری براساس شواهد تصویری موجود.
- `descent_unconfirmed`: سقوط روی کف تأیید نشد، اما سالم‌بودن نیز نتیجه‌گیری نمی‌شود؛ سیاست درخواست بررسی می‌سازد.
- `floor_lying_ended`, `upright_after_fall`: پایان/تغییر مرحلهٔ تصویری، نه بستن پرونده.
- `care_safety_*`, `care_inactivity_*`, `care_coverage_*`, `care_calibration_*`: رخداد سیاست مراقبتی در CSV.
- `frame_health_changed`, `camera_unavailable`, `tracking_lost`, `no_person_tracked`: کیفیت/پوشش پایش؛ با سلامت فرد اشتباه نشوند.
- `unknown`: شواهد ناکافی؛ وضعیت امن فرض نشود.

`pose_quality` و `detection_confidence` احتمال صحت سقوط یا خواب نیستند. سرعت‌ها برحسب طول تنه در ثانیه‌اند، نه متر در ثانیه. `source_seconds` برای دوربین زمان دیکد محلی است، نه لزوماً زمان ثبت واقعی تصویر. متادیتای کنار CSV زمان، نسخه‌ها، تنظیمات و hash وزن محلی را نگه می‌دارد.

## ۹. بهره‌برداری، نگهداری و محدودیت‌ها

- فریم و ویدئو به‌صورت پیش‌فرض ذخیره نمی‌شوند؛ فرستنده فقط متادیتای رخداد را می‌فرستد. رفتار شبکه‌ای خود وابستگی‌ها جدا بررسی شود.
- SQLite، CSV و metadata هم دادهٔ رفتاری حساس‌اند. کنترل دسترسی، رمزنگاری دیسک، backup آزموده و سیاست نگهداری لازم‌اند.
- CSV محدود می‌شود، اما دیتابیس/audit و فایل‌های run metadata پاک‌سازی خودکار ندارند. پیش از اجرای طولانی، ظرفیت و آرشیو را طراحی کنید؛ فایل WAL را در هنگام کار برنامه دستی حذف نکنید.
- زمان UTC برای deadlineهای پایدار بین restart استفاده می‌شود؛ تغییر بزرگ ساعت/NTP باید در زیرساخت کنترل و آزمایش شود. تایمر تصویر بر زمان یکنواخت منبع متکی است.
- frame guard فقط روش سادهٔ فنی است. صحنهٔ واقعاً ثابت می‌تواند شبیه فریز باشد؛ بازپخش متحرک یا جابه‌جایی هم‌اندازه ممکن است دیده نشود.
- تشخیص همهٔ سقوط‌ها، هویت فرد، نفس‌کشیدن، نبض، بیهوشی و بیماری پیاده‌سازی نشده است.
- تست موفق این پروژه به معنی صحت پیش‌بینی روی سالمندان نیست. قبل از پایلوت، مدل واقعی و زنجیرهٔ رسیدگی را انتها‌به‌انتها اعتبارسنجی کنید.

**در وضعیت خطر واقعی منتظر تایمر نرم‌افزار نمانید؛ این نمونه را تنها مسیر درخواست کمک قرار ندهید.**
